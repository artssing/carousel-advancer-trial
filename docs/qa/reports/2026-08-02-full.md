## Scope quality

呢個系統第一次真正行過。以下係 scope 本身嘅問題，唔係產品嘅判斷。

### A. 寫住嘅路徑同真 route 對唔上（行之前要靠估）

| 位置 | Scope 講 | 真實 |
|---|---|---|
| AU-08 | 「買家 token 打鑑定師 endpoint」 | 冇講邊條。`/authenticators/*` 之下**根本冇 inbox**；inbox 喺 `GET /orders/authenticator-inbox`（`orders.controller.ts:18`）。我試錯咗三條先搵到 |
| AD-01 | `finance` / `payouts` / `analytics` | 分別係 `/admin/finance/summary`、`/admin/finance/payouts`、`/analytics/admin/overview`。直接打 `/admin/finance`、`/admin/payouts`、`/admin/analytics` 一律 404 |
| WA-03 | 「提款 initiate」 | `POST /wallet/requests/initiate`，body 個 key 係 `payoutMethodId`（唔係 `methodId`）。估錯 key 會回 500，好易誤判成 bug |
| AT-01/AT-05/AT-06 | 「inbox / 搜尋 endpoint / branches endpoint」 | `/orders/authenticator-inbox`、`/orders/authenticator-search?q=`、`/authenticators/me/branches` |

建議：backend case 直接寫 method + path + 最少 body，行嘅人先唔使入 codebase 翻。

### B. 靠估或者驗唔到嘅 case

- **AD-04**（force refund on CAPTURED）：喺 UAT 到唔到 CAPTURED 而訂單又未終態呢個組合。而且 `STRIPE_MODE=mock`，「真係去到 gateway refund」喺 UAT 定義上就驗唔到。要拆做「AUTHORIZED → cancelIntent + payment CANCELLED」同「CAPTURED → refundIntent + payment REFUNDED」兩條，並且寫明後者要點砌 fixture。
- **LB-05**（DRAFT / REMOVED）：REMOVED 驗到（自己造得出）。**DRAFT 造唔到** —— `POST /listings` 一定出 ACTIVE，API 冇任何路徑產生 DRAFT，UAT DB 亦一條都冇。要麼寫明點造 fixture，要麼確認 DRAFT 仲存唔存在。
- **CB-04 / CB-05 / CB-07**（SOLD / RESERVED ribbon）：`ProductCard` 得三個 caller（`app/page.tsx`、`app/seller/[id]/page.tsx`、`app/browse/page.tsx`），三個嘅資料源都係 ACTIVE-only（LB-01 / LB-04 就係咁要求）。即係話**依家搵唔到一個 surface 餵得到 SOLD 或 RESERVED 落張卡**。呢啲 case 究竟仲驗唔驗得到（定係應該連埋 `my-listings` 一齊寫），要founder 拍板。
- **CB-08 / CC-05**：兩條都同時混咗「API 對唔對」同「畫面出唔出到」。API 果半我行到，畫面果半行唔到 —— 一條 case 兩個結論，報起上嚟好尷尬。
- **IN-04**：「未 wire 嘅頁唔係 bug」係一句 policy，冇 pass/fail 條件。佢應該係 scope 檔頂部嘅 note，唔應該佔一個 case ID（佔咗就令「幾多條 case」失真）。
- **SF-11**（3 秒內）：冇講量邊一段（用戶撳落去 → 圖出現？定 HTTP round-trip？），亦冇講用幾大張圖。我量到 9.4KB 卡 1.82s、4.4MB 卡 7.5s —— 同一條 case 可以得出相反結論。要寫死 payload 大小同計時起訖點。

### C. 重覆

- **OC-07 vs CC-01** 係同一個 assertion（「client 唔准自己計錢」），evidence 亦係同一段 code。OC-07 擺喺 backend scope，但佢驗嘅係 consumer 前端 —— 違反 `_index.md` 自己寫嘅 layer 分工（「frontend 唔好重覆 backend 已經覆蓋咗嘅邏輯」，呢度係反方向）。建議淨係留 CC-01。
- **AU-08/09/10 vs AD-02 / AN-11 / AT-02**：角色隔離喺 auth scope 寫一次，之後每個 feature scope 各自再寫一次。實際上我係同一批 curl 一次過答晒。唔一定要刪，但值得知道「10 條 case」其實係 3 條。
- **OC-04 vs LB-01/LB-04**：OC-04 明講「接返 LB-01 / LB-04」，係刻意嘅 integration 覆蓋，呢個重覆我覺得合理，記錄一下。

### D. 行嘅時候見到、但冇 case 覆蓋嘅嘢

1. **`GET /users/:id/listings` 唔係公開。** LB-04 叫佢「賣家公開 profile」，但 `PublicUsersController` 成個 class 掛住 `@UseGuards(JwtAuthGuard)`（`public-users.controller.ts:19-20`），冇 token → 401。同 SB-09（crawler 一定登出）嘅邏輯行返轉頭。冇 case 講到呢一點。
2. **Checkout 頁硬寫 tier threshold。** `app/checkout/[orderId]/page.tsx:337` 用 `>= 10000 / >= 1000` 而唔係 `tierForPrice`。Sell page 就有用 SSOT。CLAUDE.md 講明 enum-like SSOT 唔准 page 自己 hardcode，但冇一條 case 係去 catch「有人 bypass 咗 SSOT」。值得加一條 cross-cutting 嘅 static case。
3. **Admin 登入頁個語言 switcher 著住 consumer 淺色 token。** Server-rendered HTML：`class="… border-line-2 bg-white … text-neutral-text-muted …"`，貼喺 `bg-slate-950` 個 dark ops 版上面。MP-02（dark 主題）同 IN-01（switcher 樣衰係刻意）兩條都掂唔到「switcher 冇跟 portal 主題」呢件事。同 AP-02 其實係同一類問題：**共用 component 帶住 consumer 色去到第二個 portal**。可能值得一條專門嘅 cross-portal 色 token case。
4. **`AN-08` 唔會拒絕未知 channel。** 五個列明嘅值收得，但 `channel: "bogus_channel"` 一樣 `accepted: 1`。Case 只寫「收得五個值」，所以技術上冇 mismatch —— 但「未知值應該點」根本冇講過。Event name 有白名單，property 值冇。
5. **`POST /auth/login` 密碼短過 6 個字會回 400 唔係 401。** 我第一次試 `password: "wrong"` 攞到 `400 password must be longer than or equal to 6 characters`。有心人可以用呢個分辨「密碼長度規則」，雖然分辨唔到帳號存唔存在（AU-03 個真正紅線係安全嘅）。AU-02 冇講清楚要用一個夠長嘅錯密碼，落手嗰陣好易報錯。
6. **`/orders` 冇 pagination 之外，`listForAuthenticator` / 其他幾條 query 用緊寫死嘅 `take: 50` / `take: 100`**（`orders.service.ts:396, 1109, 1221`）。CC-06 只覆蓋咗買賣家訂單列表，鑑定師 inbox 撞到上限嗰陣點樣冇 case 講。
